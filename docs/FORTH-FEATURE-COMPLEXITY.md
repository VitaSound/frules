# Сложность реализации возможностей Forth

Справочник для авторов **ядра**, **embedded-портов** и **прикладного кода**: что стоит за «простой» фичей в Forth и почему минимальные системы сознательно её не включают.

Не привязан к конкретным челленджам frules — описывает **любую** Forth-систему (eForth, FlashForth, Mecrisp, Gforth, SwiftForth, …).

Два уровня справочника:

1. **Минимальное ядро (bootstrap)** — сколько примитивов зашить в asm/C, чтобы остальное определить в Forth.
2. **Сложность фич** — что стоит добавлять после bootstrap и почему embedded это урезают.

См. также: [`forth-portability.mdc`](../rules/forth-portability.mdc), [`forth-dialect-gforth.mdc`](../rules/forth-dialect-gforth.mdc), [`docs/DIALECT-TEST.md`](DIALECT-TEST.md).

---

## Минимальное ядро (bootstrap)

**Вопрос:** какой набор слов достаточно реализовать *вне* Forth (asm, C), чтобы на их базе colon definitions собрали **рабочую** интерактивную систему?

**Краткий ответ:** **~25–40 примитивов** плюс **inner interpreter** (часто не пользовательское слово, а код движка). На этом поднимают текстовый интерпретатор, компилятор `: … ;` и дальше расширяют систему только на Forth.

### Три уровня «минимума»

| Уровень | Размер | Что получаем |
|---------|--------|--------------|
| Академический | ~10–15 инструкций VM | Доказательство принципа; интерактивный Forth получается с трудом |
| Практический bootstrap (eForth, MAF, Gforth EC) | **~31–40 примитивов** | Outer interpreter, `:`, `CREATE`, control flow, базовый I/O |
| Комфортный embedded | ~50–80 примитивов + часть в Forth | ANS-подмножество, приемлемая скорость, меньше костылей |

**Критерий примитива:** слово **нельзя разумно синтезировать** из других без временных ячеек, которые сами требуют `@`/`!` и адресации словаря.

### Что обязано быть вне Forth (движок)

Не всегда оформлено как «слова», но без этого системы нет:

| Компонент | Назначение |
|-----------|------------|
| Inner interpreter | Цикл `NEXT` / `docol` / `doprim` (ITC, DTC или STC) |
| Карта памяти | Стеки, heap словаря, cold start |
| Формат заголовка слова | Link, name, code field — хотя бы неявно в примитивах `CREATE` |

Всё остальное — кандидаты на определение в Forth.

### Эталон: 31 примитив eForth (Muench / Ting)

Классический набор (~200 слов системы, включая outer interpreter и компилятор, строятся **поверх** него):

**Inner interpreter / исполнение**

- `doLIST`, `EXIT`, `EXECUTE`, `doLIT`
- `?branch`, `branch`, `next` (или эквивалент для модели циклов)
- машинный `$NEXT` (не слово пользователя)

**Память:** `@`, `!`, `C@`, `C!`

**Стеки:** `SP@`, `SP!`, `DUP`, `DROP`, `SWAP`, `OVER`; `RP@`, `RP!`, `>R`, `R>`, `R@`

**Логика / арифметика (минимум):** `0<`, `AND`, `OR`, `XOR`; **`UM+`** — единственная «настоящая» арифметика (`+`, `-`, `*`, `/` — colon definitions)

**I/O / платформа:** `?RX`, `TX!`, `!IO`, `BYE` (на MCU — UART вместо вызовов ОС)

Источник: eForth overview (vendored context — см. обсуждение в сообществе и [Gforth manual: Forth is written in Forth](../sources/gforth-manual/review--002d-elements-of-a-forth-system.md)).

### Минимум по функциональным блокам

| Блок | Минимальный набор |
|------|-------------------|
| VM | исполнение списка xt + условный/безусловный переход + литерал в код |
| Два стека | `DUP` `DROP` `SWAP` (+ `OVER` желательно); `>R` `R>` `R@` |
| Память | `@` `!` (`C@` `C!` — почти всегда для имён и строк) |
| Арифметика | одно из: `+`, `UM+`; одно сравнение: `0<`, `0=` или `=` |
| Компиляция | `CREATE`, `,`, `:`/`;`, `LITERAL`/`doLIT`, ссылка на xt (`'` или аналог) |
| Control flow при компиляции | `IMMEDIATE` **или** отдельные compile-only слова (`goto`, `-exit` в bootstrap-моделях) |
| Текстовый интерпретатор | `KEY`/`EMIT` или `?RX`/`TX!` + парсинг имени + `FIND` + interpret/compile |

**Ультра-минимум (учебный):** `@` `!` `>R` `R>` `+` `NAND` `?BRANCH` `EXECUTE` + entry для colon words — *теоретически* достаточно, но `DUP`, `IF`, `CREATE` собирают через `HERE` и временные ячейки; это bootstrap, не продукт.

### Следующий слой (~100–200 слов, уже в Forth)

Типичный «outer core» после примитивов:

- арифметика: `+`, `-`, `*`, `/`, `MOD`, `MIN`, `MAX`
- control flow: `IF`, `ELSE`, `THEN`, `BEGIN`, `UNTIL`, `DO`/`LOOP`
- словарь: `VARIABLE`, `CONSTANT`, `VALUE`, `HERE`, `ALLOT`, `'`, `[']`
- meta: `[`, `]`, `STATE`, `IMMEDIATE`
- интерпретатор: `INTERPRET`, `EVALUATE`, `QUIT`, `#`/`$`/`BASE`, `.`/`CR`
- утилиты: `DUMP`, `.S`, `SEE`

Именно этот слой делает систему **интерактивной и саморасширяемой**.

### Ловушки «слишком маленького» ядра

1. **Циклические определения** — без `@`/`!` и `HERE` нельзя завести временную ячейку для `DUP`.
2. **Производительность** — ниже ~30 примитивов размер и время кода растут резко.
3. **Модель threading** — в DTC нужен `EXECUTE`; в STC другой набор «склеек».
4. **Gforth** — компилятор написан в Forth, но старт идёт из **image file** + C-loader; «голый движок + `.fs`» без образа полный Gforth не поднимет.

### Формула рабочей системы

```
Рабочая система =
  inner interpreter (asm/C)
+ ~31–40 примитивов (стеки, память, ветвления, одна арифметика, I/O)
+ ~150–200 слов outer core (компилятор + text interpreter, на Forth)
+ прикладной словарь
```

Разделы ниже описывают **стоимость фич после** этого bootstrap.

## Как читать шкалу

| Уровень | Смысл | Ориентир (один разработчик, ядро уже есть) |
|---------|--------|---------------------------------------------|
| ★☆☆☆☆ | Почти неизбежная часть минимального ядра | часы — пара дней |
| ★★☆☆☆ | Типичное расширение «второго слоя» | несколько дней |
| ★★★☆☆ | Отдельный подмодуль, заметный объём кода | ~1–2 недели |
| ★★★★☆ | Компилятор / runtime с нетривиальными edge cases | несколько недель |
| ★★★★★ | Подсистема уровня «вторая половина системы» | месяцы |

Оценки **относительные**: зависят от целевой платформы (MCU vs desktop), стиля ядра (threaded vs token), требований к reentrancy и переносимости.

## Ядро интерпретатора

| Возможность | Сложность | Заметки |
|-------------|-----------|---------|
| Стек данных + базовые арифметические/логические слова | ★☆☆☆☆ | Основа любой системы |
| Словарь (linked list / hash), `CREATE`, `: … ;`, `IMMEDIATE` | ★★☆☆☆ | Без этого нет «настоящего» Forth |
| Интерпретатор vs компилятор (`[` / `]`) | ★★☆☆☆ | STATE, базовая meta-компиляция |
| Return stack, базовый control flow (`if`/`begin`/`do`) | ★★☆☆☆ | Согласованность глубины стека на всех путях — главная ловушка |
| Number parser (`#` / `$` / `.`), `BASE` | ★★☆☆☆ | Часто недооценивают при «минимальном» ядре |

**Embedded:** обычно останавливаются здесь + `VARIABLE` + иногда `VALUE`.

## Глобальное изменяемое состояние

| Возможность | Сложность | Что реализовать |
|-------------|-----------|-----------------|
| `VARIABLE`, `CREATE … ALLOT`, `@` / `!` | ★☆☆☆☆ | Ячейка в словаре; адрес на стек |
| `CONSTANT`, `VALUE` (read) | ★★☆☆☆ | Defining word; хранение литерала в теле слова |
| `TO` для `VALUE` | ★★☆☆☆ | Compile-time распознавание имени; запись в ячейку |
| `DEFER` / `IS` | ★★★☆☆ | Indirect threading или таблица; late binding |
| Много потоков / reentrancy для глобальных `VARIABLE` | ★★★★☆ | Либо запрет, либо per-task словари / TLS |

**Embedded:** `VARIABLE` почти всегда есть; `VALUE`/`TO` — часто; `DEFER` — реже.

**Прикладной код:** глобальные переменные — нормально для firmware с одним контекстом; для библиотек предпочтительнее аргументы на стеке (см. `forth-anti-patterns.mdc`).

## Локальные переменные

Отдель от «переменной» в смысле `VARIABLE`: это **механизм компилятора** — имена, привязанные к одному вызову слова.

| Возможность | Сложность | Что реализовать |
|-------------|-----------|-----------------|
| Стек как единственные «локали» | ★☆☆☆☆ | Уже есть; дисциплина факторизации |
| Return stack (`>r` / `r@` / `r>`) как временное хранилище | ★★☆☆☆ | Бесплатно по RAM; риск утечек и конфликта с `loop` |
| ANS `LOCALS\|` / `(LOCAL)` | ★★★☆☆ | Compile-time регистрация; runtime-фрейм; слова доступа по индексу |
| Gforth-style `{ name … }` | ★★★★☆ | Парсер блока; locals stack / control-flow tags; codegen для каждого имени |
| `{ … }` + `TO` + повторное связывание в цикле | ★★★★☆ | Дополнительные compile-time и runtime пути |
| Reentrant / nested locals с предсказуемой семантикой | ★★★★☆ | Согласование с `leave`, `exit`, quotations |

**Embedded:** locals часто **отсутствуют намеренно** (Flash, простота, предсказуемость компиляции).

**frules / Gforth:** locals допустимы и предпочтительны вместо длинных `rot`/`pick`; см. `forth-dialect-gforth.mdc`. Для переносимого ANS-кода — стек или `LOCALS|`, не `{ }`.

## Defining words и структуры данных

| Возможность | Сложность | Заметки |
|-------------|-----------|---------|
| `CREATE` без `DOES>` | ★☆☆☆☆ | Константный шаблон + allot |
| `DOES>` | ★★★☆☆ | Runtime семантика «типа»; влияет на модель словаря |
| Поля (`field`, `struct` / Gforth `end-structure`) | ★★★☆☆ | Compile-time смещения; выравнивание (`aligned`) |
| Словари / wordlists (ANS SEARCH-ORDER) | ★★★☆☆ | Контексты, `ALSO`/`PREVIOUS`, sealed vocabularies |
| OOP (`objects.fs` и аналоги) | ★★★★★ | Мета-компиляция + dispatch + lifecycle |

## Meta-компиляция и синтаксис

| Возможность | Сложность | Заметки |
|-------------|-----------|---------|
| `POSTPONE`, `[COMPILE]`, `IMMEDIATE` | ★★★☆☆ | Базовый уровень «языка расширений» |
| Parsing words (`S"`, `.(`, `[CHAR]`) | ★★★☆☆ | TIB, состояние компиляции |
| Recognizers / нестандартный синтаксис | ★★★★☆ | Gforth-специфика; высокая стоимость порта |
| Quotations (`[: … ;]`, `noname`) | ★★★☆☆ | Анонимные xt; взаимодействие с locals и GC |

## Память и адресация

| Возможность | Сложность | Заметки |
|-------------|-----------|---------|
| Статический словарь (только `ALLOT` в heap словаря) | ★★☆☆☆ | Типично для MCU |
| `HEAP`, `ALLOCATE` / `FREE` | ★★★☆☆ | Фрагментация, ошибки `-9`, политика на embedded |
| `MOVE` / `CMOVE`, выравнивание | ★★☆☆☆ | Портируемость адресных единиц — см. `forth-memory.mdc` |
| Блоки (`BLOCK`, 1024-byte sectors) | ★★★☆☆ | Legacy; на современных системах — файлы |

## Ввод-вывод и окружение

| Возможность | Сложность | Заметки |
|-------------|-----------|---------|
| `EMIT` / `KEY` / `TYPE` через UART | ★★☆☆☆ | Минимальный embedded I/O |
| `INCLUDE` / `REQUIRE`, search path | ★★★☆☆ | Файловая система или ROM-образ |
| ANS `FILE` wordset (`open-file`, …) | ★★★☆☆ | Зависимость от ОС или FAT/LittleFS |
| Аргументы CLI, `ARGV` | ★★☆☆☆ | Desktop; на MCU часто нет |

## Исключения и отладка

| Возможность | Сложность | Заметки |
|-------------|-----------|---------|
| `ABORT` / `ABORT"` | ★★☆☆☆ | Без stack unwinding |
| `THROW` / `CATCH` | ★★★☆☆ | Сохранение/восстановление стеков |
| Gforth `TRY` / `ENDTRY` / `RECOVER` | ★★★★☆ | Структурированные исключения поверх catch |
| `SEE`, backtrace, assertions | ★★★☆☆ | Инструменты разработки; на целевом MCU часто вырезают |

| Возможность | Сложность | Заметки |
|-------------|-----------|---------|
| Одинарная точность (`*`, `/MOD`, `M*`) | ★★☆☆☆ | Ядро |

| Возможность | Сложность | Заметки |
|-------------|-----------|---------|
| Standalone image / save-system | ★★★★☆ | Платформенно-зависимо |
| Cross-compiler (host → target) | ★★★★★ | Отдельный продукт (Gforth cc, Mecrisp embed, …) |
| Relocatable dictionary | ★★★★☆ | Адреса, CFA, таблицы символов |

## Почему простые embedded-системы урезают фичи

1. **Flash и RAM** — locals, FILE, FP, OOP умножают и код компилятора, и runtime.
2. **Предсказуемость** — меньше compile-time «магии» → проще отладка на железе.
3. **Reentrancy** — globals и locals без явной модели опасны в прерываниях и co-routines.
4. **Переносимость между MCU** — проще держать минимальный ANS-подмножество.
5. **Скорость порта** — новое железо = новый UART и словарь, не новый парсер `{ }`.

## Чем заменять отсутствующую фичу (любая задача)

| Нужно | Есть только минимальное ядро |
|-------|------------------------------|
| Именованные промежуточные значения | Факторинг; стек; return stack (осторожно) |
| Состояние алгоритма между вызовами | `CREATE … ALLOT` + явные индексы; буфер-запись |
| Параметризация без globals | Аргументы на стеке; xt на стеке; `DEFER` если есть |
| Динамическая память | Статические пулы; fixed-size buffers |
| Порт с Gforth на embedded | Убрать `{ }`, dynamic strings, `TRY`; проверить `environment?` |
| Порт с desktop на ANS | `ans-report.fs`; заголовок **Environmental dependencies** |

Правило frules: **не тянуть Gforth-расширение в ANS-таргет** без shim или рефакторинга — см. `forth-portability.mdc`.

## Практический выбор для нового порта

Рекомендуемый порядок наращивания (каждый шаг даёт максимум пользы на единицу сложности):

1. Ядро + словарь + control flow  
2. `VARIABLE` / `CREATE` / `@` / `!`  
3. `VALUE` (опционально `TO`)  
4. Counted strings + базовый I/O  
5. `THROW` / `CATCH` или эквивалент ошибок проекта  
6. `FILE` или ROM `INCLUDE`  
7. ANS `LOCALS|` **или** дисциплина «stack-only» (не обязательно оба)  
8. Gforth `{ }`, dynamic strings, structs — только если целевая платформа = Gforth-class

## Связь с frules

| Контекст | Ориентир |
|----------|----------|
| `dialect=gforth`, desktop, челленджи | locals, Gforth strings — OK |
| `dialect=ans`, несколько Forth | без `{ }`; стандартные wordsets |
| Embedded / cross-compile | проектировать на стеке; globals только для железа и singleton state |
| Обучение модели | в датасете явно помечать **environmental dependencies** |

При добавлении нового `forth-dialect-*.mdc` для embedded-системы — зафиксировать **подмножество wordsets** и отсутствующие фичи; сложность реализации недостающего — по таблицам выше.
